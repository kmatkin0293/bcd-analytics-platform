# Industry Demo - Pharma Clinical Trials

This is a demo SaaS application designed to imitate a CTMS (Clinical Trial Management System) provided by the fictitious company Cohortline. The demo is designed to showcase embedded analytics from ThoughtSpot.

@AGENTS.md

## Architecture

- **Design system**: Chakra UI v3 with a custom system in `src/theme/system.ts` (clay/cream/ink palette, Archivo + Spline Sans Mono fonts). `src/components/ui/provider.tsx` wraps the app in `ChakraProvider`.
- **Pages**: `/` (marketing landing), `/login` (username-only sign-in — the password field is decorative), `/home` (dashboard + Vera), `/analytics` (pipeline health dashboard), `/monitoring` (facility-country map + case flow, see below). Shared chrome (sidebar nav, user avatar) is `src/components/layout/app-sidebar.tsx`. `/config` is a hidden demo-control page (not linked in nav — reachable only by navigating there directly) for tuning Vera's query-limit gating (`src/stores/vera-usage.ts`) and defining keyboard-hotkey phrase expansion (`src/stores/hotkeys.ts`, `src/components/config/hotkey-listener.tsx`) for faster live demos.
- **Env vars**: validated centrally in `src/env.ts` via `@t3-oss/env-nextjs`. Always import `env` from `@/env` — never read `process.env` directly elsewhere. Hardcoded ThoughtSpot content IDs (liveboard, model/data-source, viz GUIDs) live in `src/config.ts`, not inline in components.
- **ThoughtSpot auth**: `POST /api/auth/token` takes a username, mints a per-user ThoughtSpot full-access token via `@thoughtspot/rest-api-sdk`, looks up the user's real display name with `UsersApi.searchUsers` (falls back to the username if `display_name` is missing), and stores `{ username, displayName, token, expiresAt }` in an httpOnly, secure `ts_session` cookie whose `maxAge` matches the token's own expiry. Read it server-side with `getThoughtSpotSession()` (`src/lib/thoughtspot-session.ts`); `GET`/`DELETE` on the same route check/clear the session. Server-side REST calls (e.g. `/api/monitoring/facility-countries`) reuse that session's token as a bearer header when constructing an SDK API client — never re-authenticate.
- **Visual Embed SDK init**: `src/components/thoughtspot/thoughtspot-auth-provider.tsx` is mounted once in the root layout so it wraps every page. Once a session exists it calls the SDK's `useInit` (so embeds work anywhere without re-initializing) and starts `startAutoMCPFrameRenderer`, which watches the DOM and swaps any MCP-sourced iframe for a fully authenticated embed automatically.
- **Vera** (the in-app AI assistant, wired on `/home`): `src/lib/vera.ts` holds the system prompt, the MCP tool allowlist/config, and the iframe-URL extraction helper. `src/app/api/vera/chat/route.ts` streams Claude (`claude-sonnet-5-5`) responses over Anthropic's MCP connector pointed at ThoughtSpot's Spotter MCP server, scoped to `THOUGHTSPOT_MODEL_ID` via the system prompt (the connector has no way to force tool arguments). `src/components/vera/` has the chat UI (multi-turn, auto-scrolling) and the Markdown+iframe renderer.
- **Monitoring** (`/monitoring`, `src/components/monitoring/monitoring-explorer.tsx`): a D3 + topojson world map of study counts by facility country, driven by live data — `GET /api/monitoring/facility-countries` runs a ThoughtSpot `searchData` query (`[Facility Country] [Study Count] [Start Date].'last 12 months'`) and returns `{ rows, nullCount }`; `src/lib/monitoring-data.ts`'s `buildCountryIndex` turns that into the map/rank-list/detail lookup structures. Note: the underlying join means a record with no Facility Country never appears as a row from that query, so `nullCount` is always `0` — the "No country recorded" row intentionally shows no number, just a "View analytics" affordance. Selecting a country embeds the `THOUGHTSPOT_LIVEBOARD_COUNTRY_STATS_ID` liveboard via `LiveboardEmbed`, filtered with `runtimeFilters` to that country's name (or the literal value `"{Null}"` for the unattributed bucket). Clicking a point on that liveboard's "Monthly Completion Rate Trend" viz — matched by `THOUGHTSPOT_COMPLETION_RATE_TREND_VIZ_ID` via `EmbedEvent.VizPointClick` (the React `onVizPointClick` prop; the payload's value is at `data.clickedPoint.selectedMeasures[0].value`, a fraction that needs `* 100` for display) — surfaces an "Open Case" button that opens a dialog prefilled with the country and completion rate. The click handler must stay wrapped in `useCallback`: a new function identity on every render makes the SDK treat `onVizPointClick` as a changed config and reload the embed.
- **Deployment**: Docker (`Dockerfile`), intended for self-hosting via Coolify — see "Docker / Coolify deployment" below.

## Docker / Coolify deployment

Modeled directly on the sibling `iot-manufacturing` project's Dockerfile/compose/Coolify setup (same company, same pattern, proven there against a real Coolify deploy). Adapted for this app's own env vars and verified here by actually building and running the image locally (`docker build` + `docker run`, hitting `/login` and `/api/monitoring/facility-countries` on the running container) — not just written and assumed correct.

* **Base image is `node:22-alpine`, not `node:20-alpine`.** `package.json`'s pinned `packageManager` (`pnpm@11.23.0`) requires Node ≥22.13 — stricter than Next.js's own ≥20.9 floor. `package.json`'s `engines.node` is set to match (`>=22.13.0`).
* **`deps` stage copies `pnpm-workspace.yaml`, not just `package.json`/`pnpm-lock.yaml`.** pnpm 11 moved its install-script allowlist (`allowBuilds`) into that file. Unlike `iot-manufacturing`, this project's `allowBuilds` doesn't need `esbuild: true` — the local Docker build succeeded without it, so don't add it speculatively.
* **Build args vs. runtime env vars — the two most likely ways to break a deploy:**
  * The five `NEXT_PUBLIC_*` vars (`NEXT_PUBLIC_THOUGHTSPOT_HOST`, `NEXT_PUBLIC_LIVEBOARD_PHARMA_CLINICAL_TRIALS`, `NEXT_PUBLIC_LIVEBOARD_FACILITY_ANALYTICS`, `NEXT_PUBLIC_LIVEBOARD_COUNTRY_STATS`, `NEXT_PUBLIC_MODEL_PHARMA_CLINICAL_TRIALS`) must be passed as Docker **build args** (`ARG`/`ENV` in the `builder` stage) — Next.js inlines them into the client bundle at build time. In Coolify, this means the per-variable **"Build Variable?" checkbox must be checked** for these five.
  * `THOUGHTSPOT_SECRET_KEY` / `THOUGHTSPOT_ORG_ID` / `ANTHROPIC_API_KEY` are real secrets and are deliberately **not** build args — Docker bakes `ARG`/`ENV` values into the image's layer history. Rather than a placeholder value per field (this project's `THOUGHTSPOT_ORG_ID` is `z.coerce.number()`, so a string placeholder like `"build-placeholder"` would itself fail validation), the `builder` stage sets `SKIP_ENV_VALIDATION=1` to bypass `src/env.ts`'s check entirely at build time — nothing executed at build time actually calls out with these values anyway. The real values must be supplied only as **runtime** env vars (Coolify: same three, "Build Variable?" left **unchecked**). Getting this backwards — or forgetting these three at runtime — doesn't fail the build; the running container crashes on startup instead with a T3 `Invalid environment variables` error, and any dynamic route shows Next's generic production error page. Check Coolify's **application/runtime logs** (not the deployment/build logs) to confirm this specific failure mode.
* **`compose.yaml` + the `pnpm docker:*` scripts are for local testing only** — `pnpm docker:up` (`docker compose --env-file .env.local up --build -d`) builds and runs the same Dockerfile locally, sourcing every var from `.env.local` so nothing has to be retyped. Coolify does not use this file; it builds the `Dockerfile` directly with its own build-arg/env-var config as described above.
* **ThoughtSpot's own CORS/CSP allowlist needs the deployed domain added separately** (Develop → Customizations → Security Settings on the ThoughtSpot instance, both the CORS allowlist and CSP Visual Embed Hosts) — otherwise embedded Liveboards and the Trusted Auth REST calls fail cross-origin once live on a new domain. Nothing to fix in this repo; it's ThoughtSpot-side config.
* The `ts_session` cookie (`src/app/api/auth/token/route.ts`) is set with `secure: true` unconditionally (not gated on `NODE_ENV`, unlike `iot-manufacturing`'s equivalent) — this requires the deployment to actually serve over HTTPS, or the cookie is silently refused by the browser and `/login` loops.

## Rules

* You have access to SpotterCode, use it for all ThoughtSpot development-related questions
* When building with ThoughtSpot, use the React components rather than the JS components
* Never use Playwright (or any similar approach) to validate what you've built. I will manually validate unless I specify otherwise.
* Never start a dev server on port 3000. I use that port and it will kill whatever I'm running.
* Anytime you start a dev server, be sure to kill it before you finish up
* Any hardcoded IDs should be added to the config file at src/config.ts rather than hardcoded in the component itself
* Vera must stay fully white-labeled — never mention ThoughtSpot, Spotter, MCP, or any vendor/tool name in anything user-facing (UI copy, status text, error messages, or Vera's own responses), even if a user asks directly what powers it
* When a Chakra component needs a native element prop that isn't part of Chakra's style props (`href`, `src`, `type`, etc.), use a `chakra('tag')` factory component (see `src/components/chakra-elements.tsx`) instead of `Box`/`Text` with `as=` — the polymorphic `as` prop doesn't retype props for TypeScript and will fail the build
* In `src/theme/system.ts`, define semantic color tokens as nested objects (`bg: { canvas: {...} }`), never flat dot-string keys (`"bg.canvas": {...}`) — a flat key still resolves for statically-inlined props (e.g. `borderColor`) but silently fails for props needing a runtime CSS variable (e.g. `bg`), because the generated declaration and its `var()` reference end up as two different custom property names. Also never let a semantic token's generated CSS variable name collide with the raw token it references (e.g. semantic `border.strong` pointing at raw token `borderStrong` — same generated name, which is self-referential and invalid) or with one of Chakra's own built-in semantic tokens (`border`, `border.subtle`, `fg.muted`, `bg.inverted`, etc.) — either collision silently zeroes out the color instead of erroring
